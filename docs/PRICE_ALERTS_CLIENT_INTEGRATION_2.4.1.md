## 1. Backend contract

### 1.1 Transport and authentication

| Item | Value |
|---|---|
| Endpoint | `POST {project}/functions/v1/price-alerts-api` (the only method accepted; anything else is `405 method_not_allowed`) |
| Body | one JSON object with an `action` discriminator |
| Platform JWT gate | **off** (`verify_jwt = false`, `supabase/config.toml`): 85Blends has no Supabase Auth session |
| Gate 1 — client API key | `apikey` header, or a legacy `Authorization: Bearer` value, must equal one of the project's configured **publishable keys** (`SUPABASE_PUBLISHABLE_KEYS`) or the legacy anon key (`SUPABASE_ANON_KEY`). Otherwise `401 unauthorized`. |
| Gate 2 — installation credential | `client_installation_id` + `installation_secret` **in the JSON body** of every action. Otherwise `400`/`401 invalid_installation_credentials`. |

Evaluation order: method → API key → database configured (`503 server_not_configured`) → JSON parse
(`400 invalid_json` / `invalid_json_object`) → `action` present (`400 action_required`) → action
(`400 unknown_action`).

The app only ever needs credentials intended for an untrusted client: the Supabase URL and the
publishable key it already ships in `Info.plist` (`SUPABASE_URL`, `SUPABASE_PUBLISHABLE_KEY`, with
`SUPABASE_ANON_KEY` as the existing fallback). No service-role key, database URL or worker secret is
needed or referenced by the client.

### 1.2 The installation credential

* `client_installation_id` — a UUID. The server requires RFC-4122 shape with version nibble `1`–`5`
  and variant `8`/`9`/`a`/`b` (`UUID_RE`), compares case-insensitively and stores it lower-cased.
  Swift's `UUID()` (random, version 4) satisfies it.
* `installation_secret` — trimmed string of **32 to 512 characters**. **Generated by the client.**
  The server stores only `sha256(secret)` (`installation_secret_hash`) and never returns, rotates or
  recovers it.
* Consequence: the secret is unrecoverable. If a client loses it, the only way forward is a **new**
  installation (new UUID + new secret). The old installation's alerts stay on the server, orphaned
  (alerts belong to an installation). There is no endpoint to delete an installation.

### 1.3 Actions

All bodies below also carry `action`, `client_installation_id` and `installation_secret`.

| `action` | Additional request fields | Success (HTTP 200) | Pro-gated |
|---|---|---|---|
| `bootstrap` | `platform` (`"ios"`/`"android"`, default `"ios"`), optional `contributor_id` (UUID), optional `app_version` (≤64), optional pair `revenuecat_app_user_id` (≤512) **and** `revenuecat_environment` (`"SANDBOX"`/`"PRODUCTION"`) — the pair must be sent together | `{status:"ready", client_installation_id, platform, pro_is_active, revenuecat_linked}` | no |
| `register_device` (iOS) | `bundle_id` (3–255), `apns_environment` (`"sandbox"`/`"production"`), `device_token` (16–1024 chars), optional `platform` (defaults to the installation's) | `{status:"registered", platform, device_id}` | no |
| `unregister_device` | `device_token` (≤1024) | `{status:"unregistered", changed}` | no |
| `set_alert` | `station_id` (UUID), `alert_mode`, optional `threshold_price`, `minimum_change`, `cooldown_minutes` | `{status:"saved", alert:{id, station_id, alert_mode, threshold_price, minimum_change, cooldown_minutes, enabled}}` | **yes** |
| `delete_alert` | `station_id` (UUID) | `{status:"deleted", changed}` | no |
| `list_alerts` | — | `{alerts:[{id, station_id, alert_mode, threshold_price, minimum_change, cooldown_minutes, enabled, last_notified_price, last_notified_at, station_name, address, city, state, latest_price, latest_reported_at}]}` | no |
| `status` | — | `{platform, pro_is_active, revenuecat_linked, active_devices, enabled_alerts}` | no |

#### `bootstrap`

`insert … on conflict (client_installation_id) do nothing`, then authenticates the presented secret
against the stored hash. So it is **idempotent** with the same credential, and it is the *only*
action that creates the server row. With an existing id and a different secret it is
`401 invalid_installation_credentials`. It also updates `client_platform`, `app_version`,
`contributor_id` (when provided) and the RevenueCat identity (when provided), then resolves current
Pro state. Omitting the RevenueCat pair leaves any previously stored pair in place.

The RevenueCat pair is how the **server** learns who is Pro: it looks the app user id up in its
webhook-fed `private.revenuecat_aliases` / `revenuecat_customers` (entitlement `pro`). The client
never asserts that it is Pro.

#### `register_device` and token replacement

Inside one transaction that first takes a row lock on the installation (`for no key update`):

1. every *other* enabled, non-invalidated device of the same `(installation, platform, bundle_id)`
   with a different token hash is **disabled** (`enabled=false, invalidated_at=now()`) — this is the
   token-rotation behaviour: registering the new token retires the old one, whatever its
   `apns_environment`;
2. the token is upserted on `(bundle_id, apns_environment, device_token_hash)`: an existing row is
   re-assigned to this installation and **revived** (`enabled=true, invalidated_at=null,
   failure_count=0`).

So registering the same token again is a no-op apart from `last_registered_at`, and re-registering
revives a device the worker had invalidated. `device_token_hash` is `sha256` of the token **string**
as sent, so its encoding must be stable (lower-case hex — `PushDeviceToken.hexString`).

#### `set_alert` (create **and** update)

An upsert on `(installation_id, station_id)`: **one alert per installation per station**.

* `alert_mode` ∈ `any_change`, `price_drop`, `at_or_below` (default `price_drop`). A missing or
  non-string value silently becomes `price_drop`; any other string is `400 invalid_alert`.
* `threshold_price`: for `at_or_below` it is required, must be a JSON **number** (strings are
  rejected) and `1 ≤ x ≤ 8` (`400 invalid_threshold_price`); for the other two modes it must be
  absent/`null` (`400 threshold_only_valid_for_at_or_below`). It is **dollars per gallon** — the
  price the observed station price must be at or below.
* `minimum_change`: JSON number, default `0.05`, `0.01 ≤ x ≤ 2` — dollars/gal.
* `cooldown_minutes`: JSON integer, default `360`, `60 ≤ x ≤ 10080`.
  Out-of-range preferences are `400 invalid_alert_preferences`.
* `station_id` must be a UUID of an existing `public.community_stations` row, else
  `404 station_not_found` (`400 invalid_alert` if it is not a UUID at all).
* Because it is an upsert that **replaces** mode, threshold, `minimum_change` and `cooldown_minutes`
  (omitted preferences fall back to the defaults, they are *not* preserved), an update must send the
  full desired state.
* It **always writes `enabled = true`**.
* Pro-gated: `403 pro_required` for a non-Pro installation, checked before validation.

Mode semantics (server-side evaluation, `private.evaluate_price_alert`; see
`supabase/functions/PRICE_ALERTS_RECOVERY.md`): `any_change` needs an earlier station price and an
absolute delta ≥ `minimum_change`; `price_drop` needs an earlier price and a downward delta ≥
`minimum_change`; `at_or_below` fires on a threshold crossing, the first qualifying observation, or a
large-enough change from the last notified price while still at/below the threshold; a current
cooldown suppresses an otherwise eligible result.

#### `delete_alert`, `unregister_device`

Both are idempotent: deleting/unregistering something that is not there is `200` with
`changed:false`. Neither is Pro-gated, so a lapsed subscriber can always remove alerts.

#### `list_alerts`

Alerts of the authenticated installation joined to `public.community_stations`, ordered by station
name, no pagination, not Pro-gated. `latest_price`/`latest_reported_at` are the station's newest
community report (both `null` when it has none).

#### `status`

Cheap server-side view: Pro state, RevenueCat link, number of active (enabled, non-invalidated)
devices and enabled alerts. `active_devices: 0` after a successful registration means the worker
invalidated the device.

### 1.4 Response encodings (derived — see note)

`price-alerts-api` returns `postgres` (porsager, `postgres@3.4.5`) rows unchanged, and the source
types them accordingly:

* `numeric(6,3)` columns (`threshold_price`, `minimum_change`, `last_notified_price`; the report
  `price`) arrive as JSON **strings** with three decimals, e.g. `"3.250"`. The code types them
  `string | null`.
* `timestamptz` columns arrive as ISO-8601 strings **with milliseconds**
  (`2026-10-05T12:34:56.789Z`), `null` when unset.
* `cooldown_minutes` (`integer`) and booleans arrive as JSON numbers/booleans.
* UUIDs arrive lower-case.

Requests are the opposite: prices and `minimum_change` must be JSON **numbers**, `cooldown_minutes`
a JSON **integer**.

> This phase made no call to the live function, so the response encodings above are derived from the
> source and the driver's documented defaults, not observed. The client decoders therefore accept a
> number **or** a numeric string for every price and a timestamp with **or** without fractional
> seconds, so either reading of the contract works.

### 1.5 Errors

Every failure is a JSON object `{ "error": "<snake_case_code>" }` with an HTTP status:

| Status | Codes |
|---|---|
| 400 | `invalid_json`, `invalid_json_object`, `action_required`, `unknown_action`, `invalid_installation_credentials` (malformed id/secret), `invalid_platform`, `invalid_contributor_id`, `invalid_app_version`, `revenuecat_identity_requires_environment`, `invalid_revenuecat_identity`, `invalid_device_registration`, `invalid_device_token`, `invalid_alert`, `invalid_threshold_price`, `threshold_only_valid_for_at_or_below`, `invalid_alert_preferences`, `invalid_station_id` |
| 401 | `unauthorized` (**API key** rejected — a configuration problem, not the installation), `invalid_installation_credentials` (**installation unknown to the server, or the secret does not match**) |
| 403 | `pro_required` (`set_alert` only) |
| 404 | `station_not_found` |
| 405 | `method_not_allowed` |
| 500 | `internal_error` (details are logged server-side only) |
| 503 | `server_not_configured` |

The two 401s mean different things and need different handling: `unauthorized` is never fixed by
touching the installation.

### 1.6 Pro behaviour

* `set_alert` is the only Pro-gated action; the gate is evaluated on the **server** from the
  RevenueCat identity linked at `bootstrap` (`resolveCurrentPro`).
* `bootstrap` and `status` report `pro_is_active` / `revenuecat_linked`.
* Send time is gated too: `private.prepare_price_alert_deliveries` skips an alert whose installation
  has no linked customer with `entitlement_id='pro' and pro_is_active`. Nothing deletes or disables
  an alert when Pro lapses — **alert rows survive a lapse and resume sending after re-subscribing**,
  as long as the installation's RevenueCat link is still valid.
* A client that believes it is Pro can still receive `403 pro_required` (webhook not processed yet,
  RevenueCat identity not yet linked, or — in Debug/Internal builds only — the Developer Pro Override
  forcing `isPro` while RevenueCat says Free).

### 1.7 What the contract does **not** have

* **No enable/disable.** `enabled` exists on the row and in responses, defaults to `true`, and the
  only writer is `set_alert`, which always sets it to `true`. Nothing in the API, the worker or the
  migrations ever sets it to `false`. In this contract "turn an alert off" is `delete_alert`, and
  "turn it back on" is `set_alert` again.
* No secret rotation / recovery, no installation deletion, no pagination, no server-side rate limit.

### 1.8 Push (worker → device)

`price-alerts-worker` sends alert pushes to `https://api.sandbox.push.apple.com` when the stored
`apns_environment` is `sandbox` and to `https://api.push.apple.com` when it is `production`, with
`apns-topic` = the stored `bundle_id`. Payload: `aps.alert{title,body}`, `aps.sound`,
`type:"price_alert"`, `station_id` (canonical UUID), `observed_price` (number). HTTP 410 and the APNs
reasons `BadDeviceToken`, `DeviceTokenNotForTopic`, `Unregistered` **permanently invalidate the
device row** (until the same token is registered again). A wrong `bundle_id` or `apns_environment`
therefore does not fail loudly — it silently kills delivery for that device.

The app's existing parser (`AppNotificationPayload`) matches this payload exactly.

## 2. Client design

### 2.1 Layers

Each layer talks only to the one below through a protocol, so each can be replaced by a fake. Every new file lives in `EightyFiveBlends/`; no existing production file was modified.

| Layer | File | Responsibility |
|---|---|---|
| Value types | `PriceAlertsModels.swift` | `PriceAlertAmount` (integer thousandths of a dollar), `PriceAlertMode` / `PriceAlertRule`, `PriceAlertPreferences`, `PriceAlertDraft`, `PriceAlert`, `PriceAlertListing` |
| Errors | `PriceAlertsErrors.swift` | `PriceAlertsAPIError` (wire) and `PriceAlertsServiceError` (what a UI switches over) |
| Wire client | `PriceAlertsAPI.swift` | `PriceAlertsAPIClienting` / `PriceAlertsAPIClient`: the exact JSON of §1, decoding, error bodies |
| Transport | `PriceAlertsTransport.swift` | `PriceAlertsAPITransport` seam + the URLSession implementation and endpoint rules |
| Credential | `PriceAlertsCredentialStore.swift`, `SystemKeychain.swift` | `PriceAlertsInstallationCredential`, `PriceAlertsCredentialStoring`, the Keychain store over a `KeychainItemAccessing` seam |
| Installation | `PriceAlertsInstallation.swift` | `PriceAlertsInstallationManager`: lazy create, persist-before-use, bootstrap, recovery |
| Device | `PushDeviceRegistrationMetadata.swift`, `PriceAlertsDeviceRegistration.swift`, `PushRegistrationService+PriceAlerts.swift` | bundle id + APNs environment, fingerprinted idempotent registration, backoff |
| Pro | `PriceAlertsEntitlement.swift` | the three-valued client entitlement and the write gate |
| Orchestrator | `PriceAlertsService.swift` | `PriceAlertsService`: CRUD, ordering, the product rules |
| Live wiring | `PriceAlertsLiveDependencies.swift` | `SubscriptionManager` / RevenueCat adapters and `PriceAlertsService.shared` |

Authentication uses only what the app already ships for an untrusted client: `SupabaseConfig.publishableKey` (falling back to the legacy anon key) in the `apikey` header. No service-role key, database URL or worker secret exists in, or is accepted by, any of it. Nothing logs: none of the new production files calls `print`, `NSLog`, `os_log` or `dump` (the tests use `dump` deliberately, to prove redaction), and every type that can hold a secret (credential, device token, RevenueCat identity, and the request that carries them) redacts every description and reflection path.

### 2.2 Installation lifecycle

Nothing runs at launch and nothing exists until needed. `existingCredential()` only reads, so a user who never used Price Alerts has no credential, and listing or deleting alerts for them is answered locally.

```
ensureReady()                       (called by saving an alert or registering a device)
  ├─ stored credential valid?  ── no ──▶ generate (UUID v4 + 64-char CSPRNG secret) ─▶ SAVE TO KEYCHAIN
  │                                                      └─ save fails ─▶ stop; nothing is sent
  ├─ Keychain unreadable (not "not found")? ─▶ throw; NEVER generate a replacement
  └─ POST bootstrap (+ RevenueCat identity, app_version)           one shared in-flight call
        ├─ 200 ─▶ session (server's pro_is_active / revenuecat_linked recorded)
        └─ 401 invalid_installation_credentials ─▶ the server holds this id under another secret
              └─ generate NEW credential ─▶ SAVE ─▶ POST bootstrap once more ─▶ else propagate
```

* One bootstrap per process, shared by concurrent callers. If the first bootstrap ran before RevenueCat was ready it is repeated once an identity is available, and only then.
* A `401 invalid_installation_credentials` from any later call triggers exactly one recovery: bootstrap the *same* credential again (cures a server that forgot the row), retry the operation once; a second refusal propagates. At most two bootstraps and two attempts per call.
* A `401 unauthorized` (API key) never triggers recovery: recreating an installation cannot cure it.
* An installation replaced by recovery keeps its alerts on the server (the backend cannot delete or reclaim one); they are orphaned.

**Credential storage.** One generic-password Keychain item (service `com.e85blends.app.pricealerts.installation`, account `installationCredential`) holding id and secret together; `kSecAttrAccessibleAfterFirstUnlockThisDeviceOnly`; never synchronizable; update-first, add-on-not-found. Not `UserDefaults`, SwiftData, CloudKit, a file or a log. It deliberately does **not** share the Referral credential's item: the backends hold independent installation tables, and a Price Alerts recovery must never be able to fork the referral identity. A reinstall on the same device finds the existing Keychain item, so the same installation (and its alerts) is reused; a restore to a new device gets none (`ThisDeviceOnly`) and starts a new installation.

### 2.3 Device registration

`PriceAlertsDeviceRegistrar` reads `PushRegistrationService` (Phase 2) and never writes to it, so a failed backend call cannot cost the app a good local token.

| Entry point | Used for | Behaviour |
|---|---|---|
| `enablePushDelivery()` | the user opts in | Free user with no installation: no prompt, no request. Otherwise prompts only if never asked, waits ≤ 10 s for the OS token, then registers. |
| `reconcileDeviceRegistration()` | a returning user on a Price Alerts screen | asks the OS for the token (never prompts), registers only what changed |
| `reconcileDeviceRegistrationIfPreviouslyRegistered()` | app-level code (e.g. app becomes active) | a complete no-op — no OS call, no network, no Keychain read — unless this install registered before |
| `disablePushDelivery()` | the user turns delivery off | fetches the token from the OS if not held (after a relaunch), asks the backend to retire it, clears the fingerprint; alerts untouched |

* **Idempotent.** After success a SHA-256 *fingerprint* of (installation id, bundle id, APNs environment, token) is stored in `UserDefaults` — never the token itself, which Phase 2 deliberately never persists. Same fingerprint within 24 h: no call. Anything different (rotated token, new installation, other environment or bundle): register. Older than 24 h: register again, which also revives a device the worker invalidated.
* **Rotation.** Registering a new token makes the server retire the old one; the client needs nothing more.
* **Contained failure.** A failed call leaves the token, the push state and the previous fingerprint untouched and starts a bounded backoff (30 s, 2 min, 10 min, then 30 min for automatic attempts; an explicit user action bypasses the wait but is still one attempt). Nothing retries by itself. Concurrent callers share one attempt.
* **Never reaches the network:** notifications denied; no token (not requested / awaiting / OS failed — including a build without the Push capability); an APNs environment that cannot be established.

### 2.4 APNs environment and bundle identifier

`register_device` needs the token's APNs environment and the app's bundle id (the push topic). A wrong value silently kills delivery (§1.8), so nothing is guessed.

**The environment depends on how the build is signed, not on the build configuration.** A development-signed build mints *sandbox* tokens; App Store, TestFlight, Ad Hoc and Enterprise builds mint *production* tokens. The `Internal` configuration therefore runs both ways, and the `INTERNAL_BUILD` flag cannot decide it.

| Build | Embedded profile | `aps-environment` | `apns_environment` sent | `bundle_id` sent |
|---|---|---|---|---|
| Debug, run from Xcode on a device | present | `development` | `sandbox` | `com.e85blends.app.ios` |
| Internal, run from Xcode on a device | present | `development` | `sandbox` | `com.e85blends.app.ios.internal` |
| **Internal, via Xcode Cloud → TestFlight** | **absent** | `production` | **`production`** | `com.e85blends.app.ios.internal` |
| Production / Release via App Store or TestFlight | absent | `production` | `production` | `com.e85blends.app.ios` |
| Ad Hoc / Enterprise | present | `production` | `production` | as built |
| Simulator | — | — | `sandbox` (a simulator token can never be delivered to) | — |
| Profile unreadable, or no `aps-environment` | — | — | *nothing registered* | — |

The bundle id is read from the running bundle, never hard-coded, so the Production and Internal identifiers cannot be swapped by this code. The environment is read from the embedded provisioning profile (`embedded.mobileprovision`, a CMS envelope around a clear-text XML plist) — absent means App Store/TestFlight, i.e. production.

### 2.5 Pro behaviour

* The client asks `SubscriptionManager.canAccessStationAlerts` (the existing feature-level gate; it routes through `isPro`) and `hasAuthoritativeProStatus`, giving three answers: `active`, `inactive`, `unresolved`. A failed or pending RevenueCat fetch is **not** treated as Free (the rule Refer & Earn already follows). No purchase, restore or RevenueCat behaviour is touched.
* **Gated on the client:** creating/changing an alert and creating a new installation. **Never gated:** listing, deleting, and keeping an existing device registration current.
* **The backend is authoritative.** `set_alert` is re-checked server-side and so is every send. If the client believes the user is Pro and the server refuses, the installation's RevenueCat link is refreshed once and the save retried once; a second refusal is `proRequiredByServer`. In Debug/Internal builds the Developer Pro Override changes only the client's answer, so a forced-Pro build is refused by the server unless RevenueCat agrees.
* **Lapse preserves.** Nothing is deleted, disabled or unregistered because Pro ended; the server stops sending for a non-Pro installation and resumes when Pro returns, with the same alert rows and the same installation.

### 2.6 Stations and alert operations

* `PriceAlertDraft` is the only way to build an alert request and takes `FuelStation.communityStationID` exactly as stored. `nil` is `stationNotEligibleForPriceAlerts`. No name, coordinates, canonical key, GasBuddy id, hash or generated UUID is ever substituted; the request carries the station id and nothing identifying a station otherwise.
* `createAlert` upserts (one alert per station); `updateAlert` sends the *full* state, carrying forward whatever was not changed, because `set_alert` resets omitted preferences to defaults. `deleteAlert` is how an alert is turned off (§1.7: the backend has no enable/disable). After every change the list is re-read from the server.
* Modes: the backend's `price_drop` and `at_or_below` are what the MVP offers (`PriceAlertRule.isOfferedInMVP`); `any_change` exists in the backend and stays representable. An unrecognized future mode decodes as `.unknown` instead of breaking the list.
* Operations that touch the alert list are serialized in request order, so a slow older refresh can never overwrite a newer save's result.

### 2.7 What Phase 3B (the UI) must wire

Nothing below is done in 3A:

1. A Price Alerts screen calls `refreshAlerts()`; saving calls `createAlert(communityStationID: station.communityStationID, …)`; "off" is `deleteAlert`.
2. Surface `stationNotEligibleForPriceAlerts` (no UUID yet), `proRequired` (paywall), `entitlementUnresolved` (call `SubscriptionManager.refreshProStatus()` and retry), `proRequiredByServer`, and `stationNotFound`.
3. The notification opt-in control calls `enablePushDelivery()`; render the returned outcome.
4. App-level code should call `reconcileDeviceRegistrationIfPreviouslyRegistered()` when the app becomes active (it is a no-op for installs that never registered) so a rotated token reaches the backend; optionally also from the AppDelegate token callback. This is deliberately not wired at launch in 3A.
5. After a reinstall the OS notification permission is reset, so `enablePushDelivery()` must be offered again; that prompt needs a user action.

### 3.2 CloudKit readiness for `FuelStation.communityStationID` (nothing was changed)

| Question | Finding |
|---|---|
| Optionality | `var communityStationID: UUID?` — optional, no default value. CloudKit requires optional-or-default; satisfied. |
| Migration | An additive optional attribute: a lightweight (automatic) migration. Existing local rows get `nil`; existing CloudKit records simply lack the field and import as `nil`. No relationship or uniqueness is involved. |
| Containers | Production app (Debug/Release, `com.e85blends.app.ios`) → `iCloud.com.e85blends.app.ios`. Internal app → `iCloud.com.e85blends.app.ios.internal`. Each entitlements file lists exactly one container, so `cloudKitDatabase: .automatic` resolves to it. |
| Field | SwiftData mirrors through Core Data: record type `CD_FuelStation`, new field **`CD_communityStationID`**, expected type `STRING` (Core Data UUID attributes are mirrored as strings). Expected from the framework's naming convention and the model comment; confirm in the CloudKit Dashboard. |
| Does assigning it export? | **Yes.** `StationsView.adoptCommunityStationIDs()` runs after community price/ethanol summaries load, assigns the UUID and calls `modelContext.save()` (only when a value changed). A SwiftData save on a CloudKit-backed model is a CloudKit export of that `CD_FuelStation` record including `CD_communityStationID`. So any build containing the Phase 2 foundation will attempt it as soon as a saved station matches community data. |
| Old records | Decode with `nil`; the field is absent from them. A `nil` is never exported as a value. |

**Later deployment requirement — a hard prerequisite, not a nicety.** Development-signed builds talk to the CloudKit *Development* environment (which creates fields on demand); TestFlight and App Store builds talk to *Production*, where a client cannot add a field, so CloudKit rejects the save of any `CD_FuelStation` record that carries the new field and that record stops syncing. Before **any** TestFlight or App Store build that contains the foundation reaches users with saved stations, for **both** containers (`iCloud.com.e85blends.app.ios` and `iCloud.com.e85blends.app.ios.internal`):

1. Make sure the Development schema contains `CD_FuelStation.CD_communityStationID` (String) — it is created the first time a development-signed build on a device signed in to iCloud exports a record with a non-nil value (open Stations with a saved station that matches community data).
2. In the CloudKit Dashboard, **Deploy Schema Changes… → Production** for that container.
3. Verify the field is present in the Production schema. No index is needed (nothing queries it).

No CloudKit schema was deployed or changed in this phase.

### 3.3 Validation

There is no Xcode on the machine that built this phase. What was run instead, and what was not:

* **Real compile and test, same language settings as the Xcode project** (Swift 5 mode, `MainActor` default isolation, approachable concurrency), on the official Swift 6.4 Linux toolchain (the compiler generation that ships with Xcode 27): all new Foundation-only sources and all new Swift Testing files, together with the existing foundation tests. **216 tests in 19 suites pass** (157 new, 59 existing). The same code also builds and passes with **zero diagnostics in Swift 6 language mode**.

The first Xcode compile of the whole app and test target will be the Xcode Cloud Test action on this branch; the smoke build from CLAUDE.md (`xcodebuild … build`) and the full `EightyFiveBlendsTests` run were not possible here.

### 3.4 Known limitations and deferred items

* **No live contract check.** §1.4's response encodings are derived from the source and the driver's defaults; the decoders accept either reading.
* **No enable/disable and no secret recovery in the backend** (§1.7); both are backend work if wanted.
* **Backend deployment state is outside this phase.** Per `supabase/functions/PRICE_ALERTS_SCHEDULER.md` the worker is not scheduled and some migrations are not applied in production; the client is written to the API's contract, which those changes do not alter.
* **Unverifiable here:** that the TestFlight build of the Internal app mints a production token (documented Apple behaviour, consistent with `docs/app-store-readiness-code-review.md` A3) — confirm on the first Internal TestFlight device.
* **Identity-lookup latency.** If RevenueCat has an App User ID but the verified App Store environment cannot be obtained, each operation can wait up to the Referral provider's 5 s bound for it before proceeding without an identity. Bounded, and only in a failure mode where Pro cannot be verified anyway.
* **Reinstall** resets the OS notification permission; push must be re-enabled by the user (§2.7).
* **Orphaned installations** (after a lost secret or a new device) keep their alerts on the server.
